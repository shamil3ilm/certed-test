# Provisioning a fresh database

Three steps, in order, for a **new, empty** Supabase project. Verified end to end against a
real project (PostgreSQL 17.6) — not only against local Postgres, which cannot exercise
`pg_cron` or Supabase's own `auth` schema.

| Step | File                                             | Destructive |
| ---- | ------------------------------------------------ | ----------- |
| 0    | Enable `pg_cron` — see below. **Do this first.** | no          |
| 1    | `01_prepare_empty_database.sql`                  | **YES**     |
| 2    | `../rebuild/0000_full_rebuild.sql`               | no          |
| 3    | `03_verify.sql`                                  | no          |

Step 2 is deliberately **not** copied here. It is generated by
`scripts/rebuild-snapshot.sh` and guarded by `scripts/check-snapshot-freshness.sh`; a second
copy would drift from the chain the moment a migration lands.

## Step 0 — enable pg_cron BEFORE the chain

```sql
create extension if not exists pg_cron;
```

Migrations `0051`, `0058`, `0059` and `0101` schedule retention inside a guard that SKIPS
silently when the extension is absent, and the chain still reports success. Apply the chain
first and you get a database with **no retention at all** — `audit_log`, read notifications,
sent emails and rate-limit rows growing without bound — while the migration log looks clean.

Observed on a fresh project: without it, zero jobs; enable it and re-run those four, and all
four schedules appear. It needs no dashboard step — an ordinary SQL session is enough.

## Step 1 is destructive

`01_prepare_empty_database.sql` runs `drop schema if exists public cascade`, because the
snapshot is a `pg_dump` and opens with `CREATE SCHEMA public`, which collides with the one
every fresh Supabase project already has. It lists the schema's tables first: **if that
returns any rows, stop** — you are not on an empty project.

## What step 3 should report

- four head markers `t` (`guardians`, `class_sessions`, `class_sessions.subject_id`, `rls_disabled_tables(text[])`)
- **zero rows** for tables without RLS — every row there is readable by anyone holding the anon key
- `pg_cron_installed = t`, and four active retention jobs

It runs clean with or without `pg_cron`: the job listing is wrapped so a missing extension
reports the remedy as notices rather than erroring, since an error at the end of a
verification script reads as "the check broke" rather than "there is nothing to report".
