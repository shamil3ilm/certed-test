# Provisioning a fresh database

Six steps, in order, for a **new, empty** Supabase project. Verified end to end against a
real project (PostgreSQL 17.6) — not only against local Postgres, which cannot exercise
`pg_cron` or Supabase's own `auth` schema.

| Step | File                                             | Destructive |
| ---- | ------------------------------------------------ | ----------- |
| 0    | Enable `pg_cron` — see below. **Do this first.** | no          |
| 1    | `01_prepare_empty_database.sql`                  | **YES**     |
| 2    | `../rebuild/0000_full_rebuild.sql`               | no          |
| 3    | `03_verify.sql`                                  | no          |
| 4    | `04_retention_jobs.sql`                          | no          |
| 5    | `05_seed_super_admins.sql`                       | no          |

Step 2 is deliberately **not** copied here. It is generated by
`scripts/rebuild-snapshot.sh` and guarded by `scripts/check-snapshot-freshness.sh`; a second
copy would drift from the chain the moment a migration lands.

## Connecting from another machine

**The direct connection string is IPv6-only.** `db.<ref>.supabase.co` publishes an AAAA
record and no A record, so on an IPv4-only network `psql` fails at DNS with
`could not translate host name` — before any password is checked. Supabase sells an IPv4
add-on; the free alternative is the pooler.

Use **Connect → Session pooler → URI**, not Direct:

```
postgresql://postgres.<PROJECT-REF>:<PASSWORD>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

- **Session** (port 5432), not Transaction (6543). These scripts are multi-statement and the
  snapshot sets session GUCs; transaction pooling does not keep a session across statements.
- The pooler username is `postgres.<PROJECT-REF>`, not the plain `postgres` of the direct string.
- Any psql version works: a 17.x client applies the 18.0-authored dump without complaint.
  Verified.

Pass the password by environment rather than inline, so it stays out of shell history:

```bash
export PGPASSWORD='...'
export PGHOST='aws-0-<region>.pooler.supabase.com' PGPORT=5432
export PGUSER='postgres.<PROJECT-REF>' PGDATABASE='postgres'
psql -v ON_ERROR_STOP=1 -f supabase/provision/01_prepare_empty_database.sql
psql -v ON_ERROR_STOP=1 -f supabase/rebuild/0000_full_rebuild.sql
psql -f supabase/provision/03_verify.sql
psql -v ON_ERROR_STOP=1 -f supabase/provision/04_retention_jobs.sql
psql -v ON_ERROR_STOP=1 -f supabase/provision/05_seed_super_admins.sql
```

Rotate the password afterwards if it passed through a shared terminal or a chat.

## Provisioning from the dashboard instead

Possible, but three properties of the browser SQL editor change what you can run, and each
one fails quietly rather than loudly:

1. **The snapshot is not pasteable as-is.** It opens with `\restrict` — a psql
   meta-command, not SQL. The editor sends statements over an ordinary connection and
   rejects it on the first line.
2. **Only the LAST statement's result is shown.** A file containing several `select`s
   displays one table and silently discards the rest, so a multi-query verification
   verifies nothing.
3. **`RAISE NOTICE` output is discarded entirely.** Anything a script reports by notice is
   invisible there.

So the dashboard route uses split, editor-shaped copies delivered alongside the maintainer's
other `.sql` bundles: the snapshot in four parts with the meta-commands stripped and the
`SET` preamble repeated in every part (each editor run is a separate session, so those
session settings do not carry over), plus a verification folded into a single result set.
Run the parts strictly in order — a skipped or out-of-order part leaves a half-built schema.

## Step 0 — enable pg_cron BEFORE the chain

```sql
create extension if not exists pg_cron;
```

It needs no dashboard step — an ordinary SQL session is enough — and it must exist before
step 4 can schedule anything.

If you provision from the **numbered migration chain**, this ordering is load-bearing:
`0051`, `0058`, `0059` and `0101` schedule retention inside a guard that SKIPS silently when
the extension is absent, and the chain still reports success. Apply the chain first and you
get a database with **no retention at all** — `audit_log`, read notifications, sent emails
and rate-limit rows growing without bound — while the migration log looks clean. Enable it
and re-run those four, and all four schedules appear.

If you provision from the **snapshot** (step 2), enabling the extension is necessary but
**not sufficient** — see step 4.

## Step 1 is destructive

`01_prepare_empty_database.sql` runs `drop schema if exists public cascade`, because the
snapshot is a `pg_dump` and opens with `CREATE SCHEMA public`, which collides with the one
every fresh Supabase project already has. It lists the schema's tables first: **if that
returns any rows, stop** — you are not on an empty project.

## What step 3 should report

- four head markers `t` (`guardians`, `class_sessions`, `class_sessions.subject_id`, `rls_disabled_tables(text[])`)
- **zero rows** for tables without RLS — every row there is readable by anyone holding the anon key
- `pg_cron_installed = t`
- **no cron jobs yet.** They do not exist until step 4; that is expected here, not a fault.

## Step 4 — retention is not in the snapshot

The snapshot is `pg_dump --schema=public --schema-only`. Cron schedules are **rows in
`cron.job`**, not DDL in the `public` schema, so the dump cannot carry them — the same
reason `scripts/rebuild-snapshot.sh` has to re-emit the `org_settings` row, the table
REVOKEs and the function grants by hand. Nothing re-emits the schedules.

The consequence is a database with no retention at all while every apply reports success,
and enabling `pg_cron` first does not change it: the extension is necessary, but the
snapshot never calls `cron.schedule`. Verified on a real project — a clean snapshot apply
with `pg_cron` already installed produced **zero** jobs.

`04_retention_jobs.sql` closes that gap, copying the four schedules from the migrations that
own them. It is idempotent (each job is unscheduled before it is scheduled) and ends with
the job listing, so the last thing you see is the four rows, all `active`.

A durable fix would add these as a fourth epilogue in `scripts/rebuild-snapshot.sh`,
alongside the three it already appends, so the snapshot provisions retention on its own.

## Step 5 — the first admin

Nobody can self-sign-up: registration binds to an admin-created allowlist row, so the first
account has to be inserted by hand and every other account is made from the UI afterwards.

`05_seed_super_admins.sql` is the **Google sign-in** path. It inserts each row as `pending`
with no setup code, which is all an OAuth first login needs — `claimAllowlistRowOnOAuth`
updates the row `WHERE auth_user_id IS NULL AND status = 'pending'`, binding the Google user
and flipping it to `active` in one step. No code is read on that path, so none is issued.
That same guard is why a revoked invite can never be re-activated by signing in with Google.

Guardian consent does not block it: `requiresGuardianConsent` is false for any non-student
role. A **student** row seeded this way would be refused on purpose — the academy is KG-12,
students are minors unless a date of birth proves otherwise, and Google sign-in captures no
guardian attestation.

For a **password** account instead, do not use this file — run
`scripts/seed-production-allowlist.mjs <email>`, which issues a one-time setup code for
`/register`. A row created by the SQL file has no code and can only be claimed with Google.

Both routes use `on conflict (email) do nothing` / skip an auth-bound row, so neither can
unbind, downgrade or re-code a live account.
